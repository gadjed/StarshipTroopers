# Орда: прототип

Навчальний прототип симуляції й рендеру десятків і сотень тисяч юнітів у браузері.
Стек: Vite + TypeScript + сирий WebGL2, HUD на звичайному HTML/CSS. Залежностей у рантаймі немає.

## Як запустити

Потрібен [Node.js](https://nodejs.org) 20.19+ або 22.12+ (разом з npm) і браузер із WebGL2.

```bash
git clone git@github.com:gadjed/StarshipTroopers.git
cd StarshipTroopers
./start_me.sh                   # ставить залежності й відкриває http://localhost:5173
```

Без скрипта: `npm install && npm run dev`. Інший порт: `./start_me.sh 8080`.
Production-збірка: `npm run build` (результат у `dist/`, переглянути — `npm run preview`).

Перші ~2 с після завантаження — «ПРОГРІВ СИМУЛЯЦІЇ» (прогрів JIT, див. нижче).

**Керування:** ЛКМ — панорама, колесо — масштаб, подвійний клік або `0` — огляд,
`Пробіл` — пауза, `M` — Прорив/Облога, `L` — авто-ліміт, `W` — хвилі, `F` — flow field,
`G` — spatial grid, `Enter` — закінчити підготовку раніше, `K` — випустити командира, `Z` — робочі зони всієї зброї (інакше зона видна лише під курсором), `N` — нова мапа, `C` — очистити.

**Будівництво** (панель унизу): `1` турель, `2` гармата, `3` міномет, `4` вогнемет, `5` електро,
`6` стіна, `7` кут, `8` мінне поле, `9` орбітальний удар, `X` знести. Натисни ЛКМ у точці й протягни
в бік, куди дивитиметься ствол (прев'ю показує робочу зону). Без протягування ствол дивиться від
бункера, а `Q`/`E` повертають його на 15°. Стіну тягни від початку до кінця: кінці «прилипають»
до кутів і кінців інших стін. Протягнуте мінне поле ставить ряд полів. `ЗНЕСТИ` прибирає все, над чим
пройде курсор. ПКМ без руху або `Esc` — скасувати; ПКМ/СКМ із рухом — панорама.
Економіки поки немає: будувати можна будь-де й будь-скільки.

**Параметри URL** (для відтворюваних тестів і бенчмарків):
`?seed=42&mode=siege&limit=100000&spawn=20000&warmup=40&zoom=6&cx=500&cy=500&flow=1&grid=1&hz=60`,
а також `auto=0` (без авто-ліміту), `waves=0` (ручний спавн; `spawn=` теж вимикає хвилі),
`destroy=2` (сила руйнування), `avoid=`, `jam=` (обхід скупчень і заторів), `jit=0` (без прогріву),
`demo=1` (зразкова оборона: кільце стін, уся зброя, міни), `zones=1` (показати робочі зони всієї зброї).
`warmup=N` прокручує N секунд симуляції до першого кадру, тож міряти можна одразу сформовану орду.
Для бенчмарків із фіксованою кількістю жуків додавай `auto=0`.
У консолі доступний `window.horde` (`sim`, `renderer`, `camera`, `state`, `stats`, `governor`).

## Архітектура

```
src/
  shared/            контракт між симуляцією і рендером: тільки дані
    constants.ts     розмір світу, ємність, типи жуків, формат інстансу
    contracts.ts     ObstacleSet, ErosionData, NavFieldData, MapData, BugFrame, HashGridView
    defense.ts       типи будівель і інструментів, формат FX-інстансу
  sim/               нічого не знає про DOM чи WebGL
    bugStore.ts      SoA-стан жуків + пул вільних слотів
    obstacles.ts     генерація скель за seed, грубий грід для колізій, будівлі-перешкоди
    erosion.ts       кратери локальної корозії скель
    defense.ts       оборона: будівлі, наведення, снаряди, вогонь, блискавка, міни, орбіта
    navField.ts      растеризація перешкод, Lazy Theta*, поле напрямків (фонова задача)
    congestionField.ts  грубе поле заторів: «обійти з іншого боку?»
    spatialHash.ts   counting sort у плоскі масиви
    simulation.ts    крок: директор → spawn → hash → пари+укуси → рух+корозія → оборона → задачі
    director.ts      хвилі й зростання спавну
    jobs.ts, heap.ts фонові задачі з бюджетом часу; купа з цілими ключами
    warmup.ts        прогрів JIT на старті
    config.ts        константи симуляції та SimParams
  app/governor.ts    авто-ліміт жуків під ≥60 FPS
  render/            нічого не знає про класи симуляції
    renderer.ts      6 draw calls на кадр, ping-pong буфер інстансів, маска ерозії
    shaders.ts       земля+оверлеї, скелі й будівлі (SDF), жуки (billboard-кулі), FX оборони
    camera.ts, glUtils.ts
  hud/hud.ts         DOM-HUD, оновлення 4 рази на секунду
  main.ts            фіксований крок, інтерполяція, введення
```

**Розділення sim/render.** Рендер імпортує лише `shared/`. Симуляція віддає назовні
`MapData` (раз на мапу) та `BugFrame` (щокадру), а це просто typed arrays і числа.
`BugStore` виділяє всі масиви з одного `ArrayBuffer`, а коли сторінка `crossOriginIsolated`
(у `vite.config.ts` уже стоять COOP/COEP) — із `SharedArrayBuffer`. HUD показує «SHARED MEMORY: ТАК».
Щоб перенести симуляцію у Worker, досить передати буфери й `SimParams`; код рендеру не зміниться.

### Стан жуків: SoA + пул

`posX, posY, velX, velY, prevX, prevY, radius, maxSpeed, shade: Float32Array`,
`type, alive: Uint8Array`, `freeStack: Int32Array`. Усі масиви виділяються один раз
на 200 000 жуків.

- **Спавн** = `freeStack[--top]`, **смерть** = `freeStack[top++] = i`, обидва за O(1).
- Індекс жука стабільний, поки жук живий. На ньому триматимуться турелі на наступних етапах.
- `highWater` — верхня межа живих індексів, і цикли йдуть до неї, а не до ємності.
  Пул видає спершу менші індекси, тож живі жуки тримаються щільним префіксом.

### Крок симуляції (фіксований, 30 Гц за замовчуванням)

1. **Cull / spawn.** Жуки з'являються у смузі 25 од. уздовж усіх чотирьох країв.
   Тип обирається за вагами, радіус ±10 %, швидкість ±15 %.
2. **Spatial hash** (`spatialHash.ts`), клітинка 4×4 од., 250×250 клітинок. Щокадру
   будується з нуля через counting sort за три проходи:
   - гістограма `cellCount[c]++`;
   - префіксна сума → `cellStart` (`numCells + 1` елемент);
   - розкладка: `sortedIndex[cursor[c]++] = i`, а заодно копіюються `sortedX/Y/R`.

   Жуки однієї клітинки лежать у пам'яті підряд, а клітинки одного рядка йдуть одна за
   одною. Тому «клітинки x0..x1 рядка y» — це один неперервний діапазон
   `[cellStart[row+x0], cellStart[row+x1+1])`. Ні `Map`, ні масивів масивів.
   Копії позицій — це і кеш-локальність, і знімок стану на початок кроку.
3. **Розштовхування** (`accumulateSeparation`), half-shell: кожна пара рахується один раз.
   Жук дивиться лише «вперед»: решта своєї клітинки, сусідня на сході й три клітинки
   рядком нижче. У відсортованому масиві це рівно два неперервні діапазони.
   Внесок додається обом жукам з протилежними знаками. Рахуються три речі:
   - м'яке розштовхування для steering (лінійне в радіусі `1.2·(rᵢ+rⱼ)`);
   - жорстка корекція перекриття, поділена за «масою» ∝ r², тож легкий жук відходить більше;
   - скалярний «тиск» Σ перекриттів (див. затори нижче).

   Кількість кандидатів обмежена (`MAX_SCAN`).
4. **Рух** (`integrate`):
   - напрямок з flow field;
   - steering `v_бажана = flow·vmax·(1−затор) + sep·push·vmax`, де Δv обмежено `MAX_ACCEL·dt`;
   - `pos += v·dt + 0.5·корекція`;
   - виштовхування зі скель, бункера й країв мапи;
   - **`v = (pos_new − pos_old)/dt`**, як у position-based dynamics. Компонента швидкості
     в стіну чи в натовп «з'їдається», тож ковзання вздовж стін виходить без окремого коду.

   Читаємо лише знімок, а пишемо у `posX/posY`, тож результат не залежить від порядку обходу.

**Затори.** Перша версія без них у режимі «Облога» колапсувала: до 52 жуків в одній
клітинці 4×4. Однопрохідна Jacobi-корекція під постійним тягом поводиться як стовп пружин,
і перекриття росте лінійно з глибиною натовпу. Векторна сума корекцій затор не показує,
бо в середині натовпу поштовхи з усіх боків взаємно гасяться. Тому жук дивиться на скалярний
тиск (суму відносних перекриттів) і при `Σ ≥ 0.3` перестає «хотіти» вперед.
Після цього натовп стабільний: близько 10 % перекриття, ~5.4 контакти на жука (майже
гексагональна упаковка) незалежно від глибини.

### Flow field (`navField.ts`)

Грід 256×256 (клітинка ≈ 3.9 од.) поверх мапи. Рахується один раз на мапу, приблизно за 80 мс.

1. **Растеризація.** Знакова відстань (SDF кола або повернутого прямокутника) від центру
   кожної клітинки до скель. Клітинка заблокована, якщо відстань менша за радіус найбільшого
   жука + 0.35 од. При меншому «роздуванні» маршрути вели в щілини, куди танк фізично
   не пролазить, і там утворювались затори-«чаші».
2. **Any-angle пошук (Lazy Theta\*)** від бункера, з повним розгортанням і без евристики.
   Батьком клітинки може бути будь-яка клітинка в прямій видимості, а не лише сусідня.
   Пряму видимість перевіряє DDA по гріду, «ліниво» й лише раз на клітинку. Результат —
   евклідова відстань `dist` і для кожної клітинки точка, на яку з неї видно шлях до цілі.
3. **Напрямок** — одиничний вектор від клітинки до цієї точки. На відкритій місцевості він
   вказує прямо на бункер, за скелею — на її видимий кут.
4. **У жука** — білінійна інтерполяція чотирьох сусідніх векторів. Заблоковані клітинки
   мають вектор (0,0) і після нормалізації випадають із суми.

**Чому не звичайний Dijkstra по 8 сусідах.** Перша версія використовувала саме його, і орда
збиралась у «зірку». Октагональна метрика квантує напрямки: цілі сектори отримують однаковий
напрямок, жуки йдуть паралельно до лінії стику секторів (осі й діагоналі) і далі сунуть нею.
A\* на жука немає: вартість навігації — кілька читань із масивів.

### Натовп: скупчення, затори, застрягання

Поверх поля діють три механізми. Кожен можна вимкнути, щоб побачити, що він дає.

- **Обхід скупчень** (слайдер, `avoid`). Груба сітка щільності 16×16 од. будується з
  `cellCount` spatial hash і дає градієнт щільності. Жук відхиляється від натовпу лише вбік
  від маршруту (компонента вздовж маршруту прибирається), тож не гальмує. Ухилення
  скасовується, якщо в той бік скеля або звідти далі до цілі. Найменша щільність часто буває
  саме в «тіні» скелі, і без цієї перевірки жуки самі набивались у кишені біля каменів.
- **Обхід заторів** (слайдер, `jam`, `congestionField.ts`). Друге, грубе поле 128×128
  з ціною клітинки `1 + 8·(ρ/0.25)²` перераховується кожні 20 кроків (~4 мс).
  Для кожної клітинки порівнюється ціна шляху в двох точках попереду: куди веде основне поле
  і куди радить поле заторів. Спільна черга біля бункера в різниці скорочується, тож реакція
  виникає лише на розвилках: «цей прохід забитий, а з іншого боку скелі вільно». Жук читає
  готові вагу й напрямок білінійно. Якщо поради майже збігаються (< 20°), лишається чисте
  any-angle поле, інакше повернулась би «зірка».
- **Відхід убік при застряганні.** Жук пам'ятає найменшу досягнуту відстань до цілі.
  Якщо 1.5 с немає прогресу і поруч скеля, він на 1.2 с відходить убік і трохи назад —
  туди, звідки, за двома бічними «пробами», ближче до цілі. За нічиєї боки чергуються.
- **Затори в натовпі** (див. вище): стиснутий жук не тисне вперед.

**Головне обмеження «Прориву».** Бункер пропускає не більше ~435 жуків/с: це обмежує довжина
кола зони прориву. За будь-якого спавну понад цю межу черга росте, доки не впреться в ліміт,
і затоплює частину мапи. «Чаші» в цьому режимі — переважно хвіст такої черги, що вперся в
скелі: вільного шляху там просто нема. На навантаженні, яке бункер встигає пропускати,
застряглих біля скель у тестах 0–0.6 % на п'яти мапах. При переповненні поле заторів робить
чергу компактною й округлою замість «хреста» з язиками за скелями.

### Руйнування: корозія скель і укуси

Кейс: велике скупчення між двома каменями, тіснява. Два механізми її розряджають
(слайдер «РУЙНУВАННЯ», `destruction`; 0 — вимкнено):

- **Корозія — локальна** (`erosion.ts`). Скеля не зменшується вся: жуки вигризають її саме
  там, де в неї впираються. Колізія повертає скелю, точку контакту й нормаль
  (`io[3..7]` у `resolve`). Якщо жук у тісняві (тиск > `CORRODE_PRESSURE`) або застряг,
  шкода `corrode` його типу йде в **кратер** трохи вглиб від точки контакту.
  - Кратер — коло, що росте з накопиченою шкодою (площа ∝ шкоді, до радіуса 4 м).
    Шкода поруч із недорослим кратером поглиблює його, тож натовп, що тисне в одне місце,
    вигризає одну виразку, а не сотні дрібних.
  - Повний кратер — вільний простір: жуки заходять у нього, впираються в його дно, і там
    з'являється наступний. Так прогризається тунель.
  - Вільний простір = поза скелями ∪ кратери (CSG-віднімання кіл). Колізія: коло, що цілком
    у кратері, скелі не торкається; коло, що зачепило матеріал біля кратера, повертається
    в кратер, якщо це ближче, ніж виходити назовні.
  - Flow field відкриває клітинки, що глибоко в кратерах; перебудова — щоразу, коли кратер
    доростає до повного розміру.
  - Рендер малює кратери в R8-маску світу (2048², blend MAX). Шейдер скелі «вирізає» по ній
    дірку з кислотною облямівкою, і тінь скелі теж стає дірявою.
  - Скеля, з якої з'їли «все здоров'я» (∝ площі, рахується разом із кратерами), розсипається.
  - Стіни гравця так **не** працюють: у них цілісна міцність, вони тріскаються й падають при 0.
- **Укуси.** Жук, що в тісняві, застряг і стоїть біля скелі (`biteReady`, рішення з
  попереднього кроку, один байт на жука), кусає сусідів, менших за себе в 1.3 раза:
  танк ≫ воїн > бігун. У жуків з'явилось `hp` (воно ж знадобиться для зброї). Звичайна
  щільна черга (облога, прорив) не кусається, лише тіснява між каменями.

**Перебудова flow field під час гри.** Доріс кратер, розсипалась скеля, змінилась оборона → поле застаріло.
Lazy Theta* займає ~80 мс, тому він став **фоновою задачею** (`jobs.ts`):
- генератор робить `yield`, коли вичерпано бюджет кроку (1.5 мс), і поле будується за десятки кадрів;
- два вихідні буфери: нове поле пишеться в задній, поки жуки й рендер читають передній; підміна атомарна;
- поле заторів — так само, з подвійним буфером того, що читають жуки.

Два неочевидні уроки V8 звідси:
1. **Важкі цикли не можна писати всередині генератора.** Генератори не отримують on-stack
   replacement, тож перебудова йшла майже в інтерпретаторі, і шматки займали 200+ мс
   замість 1.5. Генератор лишився тонким диспетчером, а роботу роблять звичайні методи
   порціями (`thetaStep(256)`, `directionRows(y0, y1)`…).
2. **Ключі купи — цілі** (відстань × 64): купа в іншому модулі викликається не інлайнено,
   і double-ключі пакувались би в HeapNumber.

### Оборона (`sim/defense.ts`)

| Будівля | Що робить |
|---|---|
| Ядро бункера | 100 000 міцності, без зброї. Прорив завдає ядру шкоду `attack×3`, у облозі — `attack×3`/с від кожного, хто торкається. 0 → «БУНКЕР ЗНИЩЕНО», за 4 с нова мапа |
| Турель | зона 80°, 300 м; черга 200 набоїв по 20/с, 0.5 с перезарядка; 4 шкоди за кулю |
| Гармата | зона 90°, 40–700 м; фугас раз на 3 с, вибух 14 м / 45 шкоди; б'є в найщільніше скупчення |
| Міномет | зона 120°, 70–550 м; навісом через скелі, політ 1.1 с + d/420, розкид 6 м + 4 % дистанції, вибух 16 м |
| Вогнемет | зона 70°, 90 м; 6 крапель/с падають біля цілі й стають зонами вогню (6 м, 2.5 с, 4.5/с). Шкодить лише вогонь, і **зони не сумуються**: жук у кількох горить як в одній. Ранній варіант зі сумуванням створював вогневі заслони, крізь які жуки не проходили (12 вогнеметів вбивали в 18 разів більше за 12 турелей); тепер крізь вогонь проходить ~83 % натовпу |
| Електро | зона 120°, 180 м; блискавка б'є в точку поруч із ціллю, чіпляється за найближчого в 3.5 м і стрибає до 8 цілей у радіусі 18 м, −28 % за стрибок |
| Стіна | 40 міцності на метр; зупиняє, жуки гризуть її (`attack` типу за секунду контакту). Зброя стріляє над стінами |
| Кут | 2500 міцності. Стіна з кутами на обох кінцях отримує ×1/3 шкоди, з одним — ×1/1.35. Колір краю стіни: бурштиновий / зелений |
| Мінне поле | 7 мін за клік (центр + шестикутник 8 м). Міна реагує на ворога в 4 м і вибухає через 1 с: 9 м / 40 шкоди. Між мінами не менше 7 м. Спрацьована міна за 25 с зводиться знову на тому самому місці (на мапі — дуга прогресу) |

**Агро на зброю.** Жук ближче 24 м до підставки зброї з імовірністю 60 % іде прямо на неї й
гризе, щойно торкнеться (решта йде далі до бункера). Зброя штампується в ту саму грубу сітку
16 м, що й командири: клітинка пам'ятає найближчу зброю, жук читає один запис. Тож турель без
охорони у вузькому місці довго не живе (у тесті три беззахисні турелі на 300 жуків/с — 45 с;
без агро дві з трьох пережили 2 хвилини). Стіни й кути агро не викликають: їх гризуть ті, кому
вони заступають шлях.

**Командири** (`КОМАНДИР`, фіолетові). Радіус 4.5 м, 3000 HP, 80 шкоди/с будівлям і ядру,
корозія скель ×40 від воїна. З'являються з кожною хвилею (1 + хвиля/2, до 6) і раз на 90 с
поодинці, коли ввімкнено хвилі; `K` або кнопка «КОМАНДИР» — випустити вручну. Аура 30 м:
жуки в ній на 30 % швидші й удвічі сильніше гризуть будівлі та ядро. Командир прошиває натовп,
розштовхуючи дрібних. Зброя бере командира в зоні першочергово, але кулі ловить натовп перед ним,
тож валять його переважно вибухи (міномет, гармата, орбіта).

Радіус командира більший за клітинку spatial hash, тож у проході пар він не бере участі. Натомість
щокроку живі командири штампуються в грубу сітку 16 м: «поруч командир» (жук виштовхується з
його кола) і «аура». Жук читає по байту з цієї сітки, без перебору командирів у гарячому циклі.

**Авторегенерація.** Будівля, яку 6 с ніхто не чіпав, відновлює 3 % міцності за секунду
(повністю — за ~33 с). Ядро бункера — після 10 с без шкоди, 0.5 %/с. Відновлена стіна знову
стає «дорожчою» для flow field.

**Зброя не б'є «в жука».** Вона обирає ціль, рахує точку прицілу з упередженням (швидкість
цілі × час польоту) і розкидом і стріляє туди. Шкоди завдає те, що реально трапилось:
- куля — першому жукові на відрізку, який вона пролетіла за крок (DDA по клітинках spatial hash);
- фугас — вибухом у першого жука на шляху або в точці прицілу;
- міномет і орбіта — вибухом у точці падіння;
- блискавка — тому, хто опинився біля точки удару, інакше розряд у землю.

Промахи й «випадкові» жертви — наслідок фізики, а не кидок кубика.

**Пошук цілі** не перебирає жуків: грубою сіткою щільності (16 м, її вже рахує симуляція) по
клітинках у дальності й секторі. Турель, вогнемет і блискавка беруть найближчу клітинку з
жуками, гармата й міномет — найщільнішу. Далі — конкретний жук у цій клітинці зі spatial hash.
Пряма видимість — по nav-гріду: скелі закривають, будівлі ні. Міномет її не потребує.
Ціль тримається, доки жива й у зоні, і переоцінюється раз на 0.4 с. Ствол повертається з
обмеженою швидкістю й лише в межах робочої зони.

**Будівлі в навігації.** Стіни, кути й підставки зброї — перешкоди для колізій (той самий
`ObstacleSet`, з запасом ємності), але для flow field це не стіни, а **дорогі клітинки**:
вхід коштує додатково ∝ міцності (`navCost`). Тож жуки обходять оборону, якщо обхід не надто
довгий. Якщо бункер обнесено повністю, вони йдуть найдешевшим шляхом крізь найслабше місце
й гризуть його. Крізь дорогі клітинки any-angle «зрізи» не проходять: шлях іде грідом.
Ослаблення будівлі на 25 % перераховує її ціну й поле.

**Усе — SoA-пули фіксованої ємності:** будівлі (4096), снаряди (16384), зони вогню (4096),
ефекти (4096). У кроці немає алокацій. Аргументи «гарячих» методів (влучання, вибух, ефект,
пряма видимість) йдуть через `Float64Array`, а не через double-параметри (див. GC нижче).
Рендер оборони — один інстансований прохід FX-шейдера (8 float на інстанс), двома draw calls:
під жуками (робочі зони, міни) і над ними (стволи, снаряди, вогонь, вибухи, блискавки, прев'ю).

### Авто-ліміт ≥60 FPS і хвилі

- **Регулятор** (`app/governor.ts`): модель «крок ≈ 2.5 мс + ціна × N». Ціна одного жука
  оцінюється з реальних замірів кроку. Двічі на секунду ліміт ставиться так, щоб крок
  вкладався в 12 мс: при 30 Гц симуляції кадр із кроком ≈ крок + рендер < 16.7 мс.
  Додатковий запобіжник — реальні пропущені кадри (>5 % → ріжемо). Ліміт лише стримує спавн
  і нікого не вбиває. Знижує швидко, підвищує повільно й лише коли ліміт справді впирається.
  Слайдер «СТЕЛЯ ЛІМІТУ» — верхня межа, понад неї жуки знімаються одразу.
  Заміряно (M1 Pro під фоновим навантаженням): ліміт сходиться до 33–41 тис., крок
  ≈ 11.5–12 мс, 60 FPS. Ціна жука росте з щільністю натовпу (0.22 → 0.27 мкс),
  і ліміт плавно йде за нею.
- **Директор** (`director.ts`): перші 60 с — **підготовка** без жуків (банер із відліком,
  `Enter` — почати раніше, `?prep=0` — без неї). Далі спавн стартує з 40/с і росте на 60/с щохвилини.
  Кожні 2 хвилини приходить хвиля: 15 с спавну ×6, 80 % жуків з одного боку мапи.
  Банер «ХВИЛЯ N · БІК», у HUD — таймер до наступної. Кількість обмежує ліміт, тож хвиля
  не може обвалити FPS.

### Прогрів JIT (`warmup.ts`)

V8 оптимізує функцію під ті гілки, які вже бачив. Перша хвиля, перший укус, перша кислота,
перший відхід убік — кожна нова гілка в гарячому циклі викидала оптимізований код
(«insufficient type feedback»). Решта циклу на 50k жуків доганялась у базовому компіляторі,
що пакує кожне дробове число: крок на 100–200 мс і ~40 МБ сміття.

Два заходи:
- гарячі проходи йдуть порціями по 2048 жуків (`HOT_CHUNK`), тож деоптимізація зачіпає лише
  решту однієї порції;
- на старті окрема маленька симуляція за ~2 с проходить усі ці ситуації. Методи класу — спільні
  функції, тож фідбек дістається основній симуляції.

| Прогрів | GC за 200 с гри (50k) | деоптимізацій гарячих функцій |
|---|---|---|
| без прогріву | 121–131 | 15–16 |
| 0.7 с | 82–87 | 10 |
| 2 с | **0** | **1** |

### Колізії зі скелями (`obstacles.ts`)

Грубий грід 16×16 од. у CSR-форматі (`cellStart` + `items`). Скеля записується в усі клітинки,
які перетинає її AABB, розширений на максимальний радіус жука, тож жукові досить перевірити
свою клітинку. Порожність клітинки перевіряється інлайн у гарячому циклі. Коло виштовхується
по радіусу. Прямокутник — у локальних координатах: від найближчої точки, а якщо центр
усередині — по осі мінімального проникнення. Скелі в кластерах перекриваються, тому до трьох ітерацій.

### Рендер

Шість draw calls на кадр (плюс перемальовування маски ерозії, коли кратери змінились,
не частіше ніж раз на 60 мс). Основні:

| Прохід | Що | Як |
|---|---|---|
| Земля | пісок, тактична сітка, оверлеї | fullscreen-трикутник; flow field (`RGBA32F`) і заповненість hash (`R8`) читаються через `texelFetch`, стрілки й лінії гріда — SDF у фрагментному шейдері |
| Тіні скель і будівель | | instanced-квади, SDF |
| Скелі, бункер, будівлі | | instanced-квади, SDF, фаска з градієнта SDF, дірки за маскою ерозії |
| FX під жуками | робочі зони, міни | instanced, вигляд за `kind` |
| Жуки | усі одним викликом | `drawArraysInstanced`, billboard-квад, «куля» у фрагментному шейдері: нормаль сфери з uv, дифуз + блік + обвідка, AA через альфу |
| FX над жуками | стволи, снаряди, вогонь, вибухи, блискавки, прев'ю | той самий буфер, атрибути зсунуті на початок верхнього шару (у WebGL2 немає base instance) |

Інстанс жука — 6 float: `prevX, prevY, x, y, radius, type+shade`. Вершинний шейдер
інтерполює `mix(prev, cur, alpha)`, тож рух плавний при будь-якій частоті симуляції.
Буфер вивантажується **одним `bufferSubData` і лише в кадрі, де відбувся крок**.
Буферів два (ping-pong), щоб не писати в той, який GPU, можливо, ще читає.
Мінімальний екранний радіус ~1 px, тож при віддаленні жуки не зникають.

## Продуктивність

Таблиця нижче — фіксована кількість жуків (`auto=0`). У звичайній грі кількість добирає
авто-ліміт. Заміри на MacBook Pro M1 Pro. Симуляція міряна в Node 26 (той самий V8, що в Chrome),
`seed=4242`, після формування орди; GPU — у Chrome через `EXT_disjoint_timer_query`.

| Сценарій | Крок симуляції | з них: hash / розштовх. / рух | GPU-кадр |
|---|---|---|---|
| 50k, Прорив | 14.5 мс | 0.9 / 6.4 / ~5 | ~2.5 мс |
| 50k, Облога | 15.8 мс | 0.9 / 7.0 / ~5 | ~2.7 мс |
| 100k, Прорив | 29.7 мс | | ~3.1 мс |
| 100k, Облога | 31.5 мс | | ~5.4 мс |

Обхід скупчень і заторів додає ~3 мс на крок при 50k, руйнування — ще ~0.5 мс.
Перерахунки полів тепер фонові, не довші за 1.5 мс на крок. Слайдери на 0 повертають
попередню швидкість (~11 мс).

На 30 Гц крок виконується через кадр (при 60 Гц дисплея).

- **50k:** кадр із кроком ≈ 14–16 мс < 16.7 мс → 60 FPS, але впритул. Тому за замовчуванням
  кількість добирає авто-ліміт, а найбільше допоможе Worker (див. нижче).
- **100k:** ≈ 0.9 с симуляції на секунду. Кадри з кроком тривають ~30 мс, без кроку ~2 мс →
  розрахунково **~30 FPS** з нерівним темпом кадрів.

Цифри FPS для 100k у headless-Chrome виявились недостовірними: rAF там видає синтетичні таймінги.
Тому перевір у справжньому вікні: `?mode=siege&limit=100000&spawn=20000&warmup=40`
і HUD («КАДР», «СИМУЛЯЦІЯ»). 60 Гц симуляції на 100k не тягне: кроків за кадр максимум 2,
тому симуляція сповільнюється замість обвалу FPS.

**Майже без GC.** До оборони під `node --trace-gc` (з прогрівом) за 200 с гри з хвилями,
руйнуванням і затором було 0 збирань сміття. З обороною й локальною ерозією (40k жуків,
облога, 20 одиниць зброї, орбітальні удари, 150 с) — 34–38 молодших збирань, найдовше ~1 мс.
Майже всі вони — у перші ~50 с, поки натовп росте й іде перша хвиля: V8 кілька разів
перекомпілює `integrateRange` під нові ситуації (порції по 2048 обмежують шкоду, але не
прибирають її). Далі сміття ~1–2 КБ на крок. Перша версія оборони пакувала аргументи
`pushFx(…)` на кожен FX-інстанс (69 збирань). Тепер інстанси пишуться на місці. Був один неочевидний момент: виклик неінлайненої функції з
double-аргументами (`resolve(x, y, r)`) змушував V8 щоразу пакувати числа в HeapNumber.
Це давало ~1 МБ сміття на крок, і вихід/вхід довелося пустити через `Float64Array`
(див. коментар в `obstacles.ts`). Друга пастка — `Math.hypot`: у V8 це варіативна
вбудована функція, яка теж створює сміття, тому в коді, що працює щокадру, її замінено
на `Math.sqrt`. Купа поля заторів використовує цілі ключі з тієї ж причини. У Chrome варто перевірити Performance-профайлером:
у записі не має бути «Minor GC» під час гри. HUD оновлює DOM лише 4 рази на секунду.

### Де межі й куди рухатись далі

1. **Перебір сусідів** — ~60 % кроку, приблизно 5 нс на кандидата. Розкладка пам'яті
   (SoA проти AoS) на це не впливає — перевірено. Варіанти:
   - менша клітинка (2 од.) з радіусом пошуку 2 клітинки: площа перебору −30 %;
   - SIMD через WebAssembly.
2. **Розкидані доступи за слотом.** Прохід руху йде у відсортованому порядку, а `posX[i]`,
   `velX[i]` тощо — за стабільним слотом, тобто розкидано. Класичне рішення — фізично
   пересортовувати SoA за клітинками раз на N кадрів і тримати таблицю `id → slot`
   для зовнішніх посилань (турелей).
3. **Web Worker.** Найбільший виграш для 100k: симуляція з головного потоку → рівний 60 FPS
   рендеру. Масиви вже вміють жити в `SharedArrayBuffer`. Потрібні подвійний буфер `BugFrame`
   (sim пише в один, рендер читає інший) і `SimParams` у SAB чи повідомленнях.
   Прохід руху паралелиться без гонок, бо пише лише у свої слоти. Half-shell пише в чужі
   акумулятори, тому для кількох воркерів або GPU краще «gather»-варіант: кожен жук сам
   читає 3×3 без записів у сусідів. Він удвічі дорожчий за кандидатами, зате без синхронізації.
4. **GPU compute (WebGPU).** Counting sort → atomics + prefix sum, далі gather-розштовхування
   і рух у compute-шейдерах. Буфер інстансів тоді взагалі не повертається на CPU.

### Відомі обмеження

- У місцях, де кластер скель утворює дуже вузьку щілину, жука, затиснутого натовпом,
  іноді вдавлює в скелю на соті частки одиниці (1 жук на 100k у тестах).
- Поле заторів грубе (7.8 од.) і реагує із затримкою до ~0.7 с.
- Після руйнування скелі flow field оновлюється із затримкою: перебудова розмазана на
  кілька десятків кадрів.
- Прогрів JIT — евристика: незвична ситуація, якої він не покрив, ще може дати одну
  деоптимізацію (у тестах — одна за 200 с).
- Перша стабільна оцінка ціни жука в регуляторі з'являється за ~0.5 с; до того ліміт 30k.
  Регулятор вважає вартість оборони частиною «ціни жука», тож із великою обороною ліміт
  нижчий (облога, 20 одиниць зброї: ~27 тис. при 60 FPS).
- Кратери — кола: тунель виходить «ланцюжком перлин», а flow field бачить його лише там,
  де кратер глибший за ~1.2 м від стінки (ґрід 3.9 м). Вузькі тунелі жуки знаходять
  тиском, а не маршрутом.
- Будівництво під жуками: вони просто виштовхуються з нової будівлі.
- Прогрів не покриває руйнування будівлі жуками (жуки обходять будівлі, тож за 2 с до цього
  не доходить), тож перша зруйнована будівля дає одну деоптимізацію.
- Ізольовані кишені між скелями (недосяжні клітинки) ведуть прямо до центру. Жуки туди
  не потрапляють, бо спавн лише по краях.

## Закладено під наступні етапи

- **Економіка:** будівництво йде через `Simulation.build/buildWall/demolishAt/orbital` —
  одна точка, де можна перевіряти ресурси й ціну. `Defense.canPlace` уже валідує місце.
- **Нова зброя:** тип у `shared/defense.ts` (таблиця `BUILDINGS`), гілка в `updateWeapon`,
  вигляд — `sdHead` у FX-шейдері. Снаряди, вибухи й ефекти — готові пули.
- **Різна поведінка типів:** `type[i]` + таблиця `BUG_TYPES`. Гілки поведінки краще робити
  окремими проходами за типом, а не `switch` у гарячому циклі.
- **Worker/GPU:** див. розділ «Де межі».
